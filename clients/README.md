# Apollia host-driving SDK clients

Typed clients a **host application** uses to **drive** an Apollia runtime over
its HTTP API (`/api/v1`): submit tasks, open chat sessions, stream results,
inspect the audit trail. This is the opposite direction from `sdk/apollia`,
which is the kit for *authoring* agents that run *inside* the runtime.

Both clients are **generated from the OpenAPI spec** the runtime serves at
`GET /api/v1/openapi.json`, so they cannot drift from the wire contract. Do not
hand-edit generated files; change the Rust handlers and regenerate.

| Client | Path | Generator |
|---|---|---|
| TypeScript | `clients/ts` | `openapi-typescript` (types) + `openapi-fetch` (runtime) |
| Python | `clients/python` | `openapi-python-client` |

## Contract

- Base URL over TCP: `http://127.0.0.1:7771`, all routes under `/api/v1`.
- Auth: `Authorization: Bearer <token>` where the token is at
  `~/.apollia/api-token` (mode 0600), generated by the daemon on first boot
  when `[api] require_token = true` (the default). The Unix socket is
  local-trust and needs no token.
- Stability: `/api/v1` is a versioned, stable contract. Breaking changes ship
  under `/api/v2`; `v1` is never mutated incompatibly.

## Regenerating

```sh
# Against a running daemon (refreshes the committed spec first):
bash clients/regen.sh --from-daemon

# Or from the committed spec only:
bash clients/regen.sh
```

The committed spec lives at `clients/openapi.json`.

## Demo

`clients/examples/demo_python.sh` starts a real daemon, installs the package
`clients/examples/echo` (an `apollia.toml` and one workflow that returns its
input, so no model is needed), and launches that workflow end-to-end through
the generated Python client over TCP + token. See that script for the exact
commands. It starts and stops its own daemon, and refuses to run while another
runtime is up.

The package carries its own test, run from its folder with the SDK installed:

```sh
cd clients/examples/echo && python -m pytest tests
```
