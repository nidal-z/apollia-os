# ADR-031: Unified plan model in apollia-core

- Status: Proposed
- Date: 2026-06-10

## Context

Apollia has three divergent representations of an execution plan, and the
conversational plan-mode epic needs one.

Today:

- `apollia_oria::plan::{ExecutionPlan, PlanStep}` is the engine's internal DAG
  (`step_id`, `description`, `tool_hint`, `depends_on`, `model_hint`), validated by
  `reasoner::validate_steps` + `topo::topological_sort`.
- `apollia_core::plan_alternatives::TaskPlanStep` is a near-identical duplicate,
  carried in `RuntimeEvent::PlanApprovalRequired`, in the plan-gate decision
  (`PlanGateDecision::Edited`), and in the plan_a/plan_b RLHF feature.
- The desktop gate UI re-declares the same shape again in TypeScript.

None of these carries a per-step rationale or any provenance (why a step exists,
when it was added, which revision introduced it). Replanning mutates the live plan
in place: `PlanRepository::begin_replan` deletes pending steps and bumps a counter,
so there is no construction history and nothing to replay.

The conversational plan-mode epic makes the plan a first-class, agent-managed,
auditable artifact shared by: the chat plan subsystem (a new actor and tool
surface), the ORIA orchestrated engine, the desktop DAG view, the audit/replay
journal, and the CLI. That artifact must carry a per-step rationale and provenance
and must support a mutation log (history and deterministic replay). Three diverging
shapes cannot support this without triplicating the validation, the UI mapping, and
the audit capture.

Per the anti-bloat policy (ARCHITECTURE Section D) a type belongs in `apollia-core`
only when three or more crates use it. A unified plan type qualifies (`apollia-core`,
`apollia-oria`, `apollia-runtime`, `apollia-desktop`, `apollia-cli`). This is also a
new cross-crate type and a breaking public-API change (ARCHITECTURE Section E), so it
is decided here before any code.

## Decision

We adopt a single plan model in a new `apollia_core::plan` module, and we migrate
the engine and the plan gate onto it.

The module defines:

- `Plan { plan_id, scope: PlanScope, revision: u32, status: PlanStatus, steps: Vec<PlanStep> }`
  where `PlanScope` is `Session(SessionId)` or `Task(TaskId)` so the same type serves
  both the chat path and orchestrated runs.
- `PlanStep { step_id, title, description, status: StepStatus, depends_on: Vec<StepId>,
  tool_hint: Option<String>, model_hint: Option<String>, rationale: Option<String>,
  provenance: StepProvenance }`.
- `StepProvenance { origin: StepOrigin, reason: Option<String>, at: i64 }` with
  `StepOrigin = Initial | Replan(u32) | UserInject | AgentEdit`.
- `PlanMutation { kind: PlanMutationKind, step_id: Option<StepId>, reason: Option<String>,
  before: Option<PlanStep>, after: Option<PlanStep>, at: i64 }`, the unit of history,
  audit, and replay.
- `validate_plan(&[PlanStep]) -> Result<(), PlanValidationError>`: unique ids,
  resolvable dependencies, acyclic. The logic moves here from
  `apollia_oria::reasoner::validate_steps` and `topo`, which become thin callers.

The module is pure types plus the validation helper: no async, no business logic,
framework-agnostic, in line with the anti-bloat policy.

We migrate `apollia_oria::plan::{ExecutionPlan, PlanStep}` and the existing
plan-approval gate (`PlanApprovalRequired` payload, `PlanGateDecision::Edited`) to the
unified type,
and we re-express `TaskPlanStep` as `apollia_core::plan::PlanStep` so the plan_a/plan_b
feature stops duplicating the shape. `rationale` and `provenance` are optional, so the
first plan generated by the Reasoner can omit them (the thinking trace already justifies
the initial plan); they are populated on every later mutation (add, modify, remove).

`PlanRepository` gains nullable `rationale` and `provenance` columns (additive
migration, `CREATE TABLE IF NOT EXISTS` plus `ALTER TABLE ADD COLUMN`); existing flows
are unchanged when the fields are absent.

## Alternatives considered

### Keep three types, share only the validation (rejected)
**For:** smallest immediate change, no migration.
**Against:** perpetuates the divergence, forces triplicate UI and audit mapping, and
gives no single place to attach rationale and provenance. The epic would inherit the
existing fragmentation.

### Put the unified type in apollia-oria, not in core (rejected)
**For:** the engine already owns plan logic.
**Against:** the chat path (`apollia-runtime`) and the desktop must not depend on the
heavy `apollia-oria` crate just to name a plan. `apollia-core` is the shared-types home
and the anti-bloat threshold (3+ crates) is met.

### Keep `PlanStep` unchanged, store rationale/provenance in a side table (rejected)
**For:** no change to the step type or its serialization.
**Against:** provenance is intrinsic to a step and must travel with it through events,
serialization, and the audit journal. A side table keyed by `step_id` desyncs from the
step it describes and complicates replay.

### Chosen: unified type in core plus migration
**For:** one representation, one validation, one renderer, one audit mapping; rationale
and provenance travel with each step, which is the precondition for reason-per-block,
construction history, and replay.
**Compromis acceptés:** a breaking public-API change and a coordinated migration of
`apollia-oria` and the plan gate; `apollia-core` grows by one module (bounded, and
justified by 3+ crate usage).

## Consequences

**Positives:**
- Single source of truth for plans across chat, orchestrated, desktop, audit, CLI.
- Per-step rationale and provenance unlock reason-per-block, construction history, and
  deterministic replay of plan construction.
- One desktop renderer and one audit-capture path instead of three.

**Negatives / Compromis:**
- Breaking change to the `apollia-core` public API and to the serialized
  `PlanApprovalRequired` / `PlanGateDecision` payloads; consumers update in the same change.
- The migration of `apollia-oria` and the gate must land atomically (or behind a
  short-lived internal shim) to keep the workspace green.

**Neutres / À surveiller:**
- `apollia-core` size: keep the module types-only, no logic creep.
- Audit-journal serialization stability: version the plan schema so replay of older
  runs stays sound.

## Architectural principles

- Anti-bloat (Section D): satisfied, the type is shared by 3+ crates.
- Principle #5 (one actor, one responsibility): unaffected, the module is pure types.
- Principle #7 (non-negotiable safeguards): unaffected, plan steps remain governed by
  the `StepBudget` in ORIA and in the chat loop.
- Principles #1 and #2 (local-first, zero external dependency): no new dependency.
