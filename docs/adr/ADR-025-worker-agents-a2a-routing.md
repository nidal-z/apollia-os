# ADR-025: Worker agents and A2A routing

- Status: Accepted
- Date: 2026-06-04

## Context

The tool subsystem gives agents access to a wide ecosystem of third-party tools,
but having access to tools is not the same as knowing how to use them. For
complex domain tasks (spreadsheets, CSV, PDF, SQL), the model must know which
methods to call, in what order, which guardrails to respect, and how to handle
format-specific errors. Injecting that knowledge into the prompt as a long
instruction block works on frontier models but degrades sharply on the small
local models (7-14B) that Apollia targets: they hallucinate API calls, ignore
guardrails after a few steps, and lose the thread on multi-step tasks. Domain
expertise needs to be encoded in code, not re-injected into context on every
call.

Once domain expertise lives in agents, those agents must be composable. A
director agent needs to invoke a worker by capability without knowing the
worker's name, its file path, or its execution state. That requires resolving a
call by skill, deciding the invocation mode, defining the result shape, and
settling the trust boundary between a director and the worker it calls.

## Decision

We adopt the Worker Agent pattern (domain expertise compiled into a constant
system prompt, the agent declaring A2A support) together with skill-based A2A
routing: a director invokes a worker by `skill_id`, synchronously with a
timeout, the runtime rejects ambiguous skills, and a worker has no access to the
director's memory.

### Worker Agent pattern

A worker agent encodes its domain expertise in a constant `SYSTEM_PROMPT`
(guardrails, call patterns, import rules) so the expertise is model-agnostic and
the guardrails are not bypassable by a forgetful model. It declares the pip
packages it needs in its manifest, which the runtime installs during the
`INITIALIZING` phase (fail fast on a missing package). It declares A2A support so
it is discoverable by any director. It runs with a low step ceiling and low
temperature for determinism, and it reports domain errors through stable codes.

Authoring uses the decorator-first AgentKit
([ADR-023](ADR-023-sdk-agentkit-design.md)): a worker is an `@agent` class whose
`@skill` methods are its A2A surface. There is no worker base class to inherit.
The runtime contract stays a `__apollia_manifest__` dict plus an async
`__apollia_dispatch__(task, ctx)`, both generated by `@agent`.

### Skill-based A2A routing

A director invokes a worker through `ctx.a2a` (the caller-facing API is defined
in [ADR-024](ADR-024-sdk-runtime-contract-ctx.md)). Routing is by `skill_id`,
not by agent name, so the director stays decoupled from which agent serves the
skill.

- Skill resolution scans agents that support A2A and are active or degraded. If a
  `skill_id` is declared by more than one such agent, resolution returns an
  ambiguous-skill error (`AmbiguousSkill`) that the director must handle. The
  runtime applies no silent round-robin or priority. Registration of a duplicate
  skill id succeeds; the conflict is reported at resolution, where the full set
  of active agents is known.
- Invocation is synchronous with a configurable timeout (default 120 seconds):
  the call blocks until the worker returns or the timeout expires. A
  fire-and-forget mode is intentionally not offered.
- The result is the worker's business output, returned to the director without
  extra wrapping; the worker owns its response shape.
- Trust model: the runtime never injects memory automatically, and that holds
  across A2A. A worker receives only the explicit payload, has no access to the
  director's memory, and writes to its own namespace. If a director wants to
  share context, it serializes that context into the payload.
- A worker invoked through A2A may itself invoke another worker; the per-agent
  StepBudget, the A2A timeout, and a delegation hop limit (`max_hops`, default 5)
  bound runaway recursion.

The runtime also exposes A2A discovery and delegation over the local REST API
and a CLI filter for listing A2A-capable agents and their declared skills.

## Alternatives considered

### Markdown skills injected into context (rejected)
- Pros: flexible, zero per-domain development, the pattern used by frontier
  models.
- Cons: significant degradation on small local models, context-window pressure,
  bypassable guardrails, and no advantage for the local-model case that is the
  product differentiator.

### Specialized atomic tools per domain (rejected)
- Pros: consistent with the existing tool layer, no new concept.
- Cons: an atomic tool does not know the calling sequence or the domain error
  patterns, so the model still improvises, and guardrails cannot be encoded in a
  tool.

### Resolve A2A calls by agent name (rejected)
- Pros: direct addressing.
- Cons: strong director-to-worker coupling that breaks encapsulation; skill-based
  targeting keeps the director independent of the serving agent.

### Asynchronous fire-and-forget invocation (rejected)
- Pros: non-blocking delegation.
- Cons: needs a correlation and callback mechanism neither the runtime nor the
  SDK provides; synchronous request-response covers the expected cases and keeps
  the mental model a function call.

### Automatic memory injection toward the worker (rejected)
- Pros: convenient context sharing.
- Cons: violates memory-at-agent-initiative and creates opaque behavior; explicit
  payload passing keeps sharing visible.

### Chosen: Worker Agent pattern plus skill-based synchronous routing
- Pros: model-agnostic expertise with non-bypassable guardrails, fail-fast
  dependency installation, decoupled skill-based invocation, an explicit and safe
  trust boundary, and a simple function-call mental model.
- Trade-offs: per-domain development effort, venv warm-up time at first start,
  and recursion depth bounded by the StepBudget, the timeout, and a `max_hops`
  limit (default 5) as the backstop.

## Consequences

- Positive: workers run well on small local models, domain guardrails are
  compiled in, declared packages are auditable in the manifest, a director
  delegates by skill without coupling, ambiguous skills are an explicit runtime
  error, and the trust boundary prevents accidental memory leakage.
- Negative / trade-off: a synchronous long delegation blocks the director's
  current step until the timeout, context sharing must be serialized into the
  payload explicitly, and recursion depth is bounded by the StepBudget, the
  timeout, and the `max_hops` limit.
- Watch: real-world A2A recursion patterns, the cost of skill resolution under
  many active agents, and venv warm-up time on modest hardware.

## Architectural principles

- Principle #1 (Local-first): every A2A invocation stays in-process; no data
  leaves the machine.
- Principle #2 (Zero external dependency): a worker's pip packages are
  dependencies of the agent, not of the runtime, which runs with no worker
  installed.
- Principle #3 (Minimal contract): the worker is an `@agent` class with `@skill`
  methods; the AIP contract stays a `__apollia_manifest__` dict plus an async
  `__apollia_dispatch__(task, ctx)`, both generated by `@agent`.
- Principle #4 (Fail fast): declared packages install at `INITIALIZING`, so a
  missing package degrades the agent immediately rather than at runtime.
- Principle #6 (Memory at agent initiative): a worker receives only the explicit
  payload and never the director's memory.
- Principle #7 (Non-negotiable safeguards): the A2A timeout, the `max_hops`
  limit, and each agent's StepBudget are enforced by the runtime and not
  bypassable from Python.
